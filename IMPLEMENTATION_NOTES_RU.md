# Реализация контроллеров и веб-прототипа

## Что добавлено

- Реализован `CheckupController` (`/api/checkup`): назначение медосмотра администратором, удаление назначения с защитой от удаления связанного с приёмами медосмотра, просмотр всех назначений администратором и собственных назначений пациентом.
- Реализован `UserController` (`/api/user`): профиль, список пользователей, обновление ФИО и удаление пользователей; создание, получение и удаление специальностей; получение врачей по специальности.
- Добавлены request/response DTO для новых операций.
- Заполнены имеющиеся Thymeleaf-шаблоны и добавлены CSS/JS: вход (ожидает AuthController), профиль по ролям, панель администратора, расписание, работа врача с записями медкарты, просмотр карт и медосмотров пациента.
- Добавлен общий клиент `HospitalApi`: все API-запросы отправляются методом POST с JSON и используют cookie текущей сессии.

## Соответствие UML

Маршруты и названия методов `CheckupController` и `UserController` соответствуют разделу «Описание пакетов и классов» в `report.odt` и диаграмме классов. Путь `/api/user/specialization/update` сохранён буквально как в UML, хотя в описании UML этот метод обозначен как удаление специальности. Изменять диаграммы не потребовалось.

## Контракты новых запросов

Все операции ниже используют HTTP POST.

| Endpoint | JSON запроса | Успешный ответ |
|---|---|---|
| `/api/checkup/create` | `{"patientId": 12, "specializationIds": [1, 3]}` | `CheckupResponse` |
| `/api/checkup/delete` | `{"checkupId": 5}` | `{"success": true}` |
| `/api/checkup/get` | `{}` или `{"patientId": 12}` (идентификатор пациента можно передать администратору) | `CheckupResponse[]` |
| `/api/user/delete` | `{"userId": 12}` | `{"success": true}` |
| `/api/user/update` | `{"userId": 12, "lastName": "Иванов", "firstName": "Иван", "patronymicName": "Иванович"}` | DTO пользователя соответствующей роли |
| `/api/user/profile` | без тела | DTO текущего пользователя |
| `/api/user/get` | без тела | DTO пользователей (только администратор) |
| `/api/user/specialization/create` | `{"name": "Терапевт"}` | `SpecializationResponse` |
| `/api/user/specialization/update` | `{"specializationId": 2}` | `{"success": true}` |
| `/api/user/specialization/get` | без тела | `SpecializationResponse[]` |
| `/api/user/specialists` | `{"specializationId": 2}` | `DoctorResponse[]` |

Ошибки новых API возвращают соответствующие HTTP-статусы (400 — некорректный запрос, 403 — нет доступа/сессии, 404 — объект не найден, 409 — операция конфликтует с существующими связями) и, где это уместно, `{"message": "..."}`.

## Интеграция AuthController

`AuthController.java` намеренно не изменялся. Интерфейс входа и форма регистрации уже подготовлены, но они требуют реализации другого разработчика. Предлагаемый формат, использованный фронтендом:

- `POST /api/auth/login`: `{"id": 123, "password": "..."}`; сервер устанавливает HttpOnly-cookie `token`.
- `POST /api/auth/logout`: без обязательного тела; сервер завершает сессию и очищает cookie.
- `POST /api/auth/signup`: `{"role":"PATIENT|DOCTOR", "lastName":"...", "firstName":"...", "patronymicName":"...", "password":"...", "gender":true}` для пациента; для врача вместо `gender` передаётся `specializationId`.

Это согласованный фронтендом контракт-предложение, а не описание готовой реализации AuthController. При получении фактического кода AuthController запросы фронтенда следует сверить с его DTO и названиями полей.

## Ограничения существующей реализации, которые не менялись

1. Пациентский `/api/appointment/get` возвращает только приёмы, уже назначенные этому пациенту. В существующем API нет метода получения свободных слотов, поэтому интерфейс пациента не может показать список для новой записи и выбрать `appointmentId`.
2. По UML требуется перенос и отмена с сохранением истории. В текущей модели `Appointment` нет поля статуса, а существующий `/api/appointment/delete` удаляет сущность. Для полноценной реализации потребуются статусные значения (например, active/cancelled/rescheduled/completed), отдельные API-операции отмены/переноса и выдача доступных слотов.
3. Существующий `CheckupResponse` и модель `Checkup` содержат пациента и список специальностей, но не дату, врача и состояние медосмотра. Поэтому страница пациента показывает назначенные специальности и номер назначения, а не полное расписание/статус.
4. `AccountService.updateUser` позволяет менять только ФИО; изменение пола пациента или специальности врача отсутствует в существующем сервисном контракте.
5. `AppointmentService.addPatientToAppointment` сравнивает специальность без ограничения одним календарным днём: наличие другого активного приёма у того же специалиста может заблокировать запись в другой день. Это не совпадает с правилом из технического задания «не более двух активных записей к одному специалисту в день».
6. В `AppointmentService.addPatientToAppointment` проверка временного конфликта использует строгое `< 15` минут; формулировка ТЗ «±15 минут» может подразумевать включительную границу.
7. `AppointmentController.entry/record` разрешает врачу читать карту любого пациента по ID; в UML врачу доступны карты его пациентов. Стоит дополнительно ограничить чтение карт списком пациентов данного врача.
8. В `WebController` для неавторизованных/неподходящих по роли пользователей некоторые ветви возвращают имя представления `pages/profile`, но такого шаблона в архиве нет. Файл `WebController.java` оставлен без изменений по вашему требованию.
9. `AppointmentController` и `AuthController` оставлены исходными. Их сигнатуры и поведение не менялись.

## Сборка и проверка

JavaScript-файлы проверены Node.js через `node --check`; все 17 HTML-шаблонов прошли базовый разбор HTML. Полную Maven-сборку выполнить не удалось: в архиве отсутствовал `.mvn/wrapper/maven-wrapper.properties`, а Maven wrapper не смог скачать Maven из Maven Central в данной среде. В проект добавлен файл wrapper properties с URL Maven 3.9.11; после появления доступа к Maven Central можно выполнить `bash mvnw test` (или `./mvnw test`, если выставить executable bit для `mvnw`).
